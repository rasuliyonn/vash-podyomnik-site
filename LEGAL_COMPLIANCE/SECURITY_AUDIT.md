## 2. Найденные проблемы

### 2.1. Критические

**S-01. Пароль администратора по умолчанию.**

- Где: lib/admin.php, pages/admin/login.php.
- Риск: доступ к заявкам (ФИО, телефон, email) любого лица; утечка ПД; ст. 272 УК РФ, ст. 13.11 КоАП.
- Исправлено: admin_password_is_default(); принудительный редирект на /upravlenie/settings?force=1; остальные разделы недоступны; предупреждение в интерфейсе.

**S-02. Отсутствие ограничения попыток входа.**

- Исправлено: таблица login_attempts (хеш IP), лимит 10 за 15 минут, задержка 400 мс, очистка при успехе.

**S-03. Исполняемые файлы в uploads/.**

- Риск: если фильтр расширений будет изменён или обойдён — RCE.
- Исправлено: uploads/.htaccess запрещает .php/.phtml/.phar/.pl/.py/.cgi/.sh и др.; Options -Indexes.

### 2.2. Высокие

**S-04. Открытые служебные каталоги.** docs/, scripts/, seo-content/ не были закрыты; .md уже блокировался, но .py/.bat — нет. Исправлено RewriteRule и FilesMatch.

**S-05. Ошибки отправки формы скрывались.** JS показывал успех при 400/500. Исправлено: обработка JSON, статус, блокировка кнопки, сброс только при успехе.

**S-06. Отсутствие серверной валидации email и длины полей.** Исправлено: filter_var, ограничения длины, проверка обязательных полей, honeypot, rate limit.

**S-07. XSS-риск в пользовательских полях.** Вывод экранируется e() (htmlspecialchars ENT_QUOTES), JSON-LD формируется из констант/данных без пользовательского HTML. CSP ограничивает источники. Остаточный риск — inline-скрипты (unsafe-inline) и компрометация внешнего mc.yandex.ru; рекомендуется перейти на nonce/hash при возможности.

### 2.3. Средние

**S-08. SQL-инъекции.** Запросы к заявкам и настройкам — prepared statements. Фильтр статуса — whitelist. В equipment-edit имя таблицы интерполируется, но только из фиксированного набора вызовов; пользовательских значений нет. Риск низкий.

**S-09. Cookie согласия читается JS.** По дизайну (нужно менять настройки) HttpOnly невозможен. Содержимое нечувствительно (флаги категорий). CSP снижает риск XSS. Для сессии админки HttpOnly установлен.

**S-10. База SQLite в webroot.** Защита — data/.htaccess и FilesMatch. При nginx/отключённом AllowOverride файл может быть доступен. Открытый риск; рекомендация — вынести data/ за DocumentRoot или настроить deny на сервере.

**S-11. Резервное копирование.** В коде нет автоматического бэкапа; владельцу нужен регламент (ежедневно, хранение вне сайта, шифрование, проверка восстановления).

### 2.4. Низкие

- security.txt ссылался на /terms — исправлено на /privacy.
- Нет X-Permitted-Cross-Domain-Policies — добавлено.
- Админка не имела no-store — добавлено.
- HSTS без preload — достаточно для shared-хостинга; preload требует уверенности в HTTPS на всех поддоменах.
- Нет 2FA — рекомендуется для админки, но на shared-хостинге требует внешнего сервиса.

## 3. Проверенные механизмы

| Проверка | Результат |
|---|---|
| SQL-инъекция в поиске заявок | prepared statement + LIKE-параметр, статус whitelist |
| XSS в имени/городе | вывод через e(); проверить вручную: <script> в поле не исполняется |
| CSRF админки | токен в сессии, hash_equals |
| Загрузка .php через works | расширение не входит в whitelist; getimagesize |
| Загрузка .php через документы | whitelist pdf/doc/xls/txt/zip; .php отклоняется |
| Прямой доступ к data/site.sqlite | на Apache блокируется .htaccess; локальный PHP-сервер .htaccess не читает — проверять на проде |
| Заголовки | CSP, HSTS, X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy |
| Cookie | vp_consent SameSite=Lax, Secure на HTTPS; vp_admin HttpOnly, Secure на HTTPS, SameSite=Lax |
| Ошибки PHP | display_errors=0 в index.php; журналирование включено |

## 4. Остаточные риски

1. Shared-хостинг: доступ к файлам БД и логам зависит от настроек провайдера; нужен договор и проверка прав.
2. CSP содержит unsafe-inline (инлайн-инициализация счётчика и стили). Снижает защиту от XSS, но не создаёт прямой уязвимости.
3. Нет WAF/антибот-сервиса; rate limit и honeypot — базовые меры.
4. Нет автоматического контроля целостности файлов; рекомендуется периодически сверять с git.
5. Утечка через третьи сервисы (хостинг, Метрика) не контролируется кодом; нужны договоры и настройки приватности.
6. Резервные копии и доступ сотрудников — вне репозитория.

## 5. Рекомендации

1. Сразу после деплоя сменить пароль админки на уникальный (12+ символов), включить 2FA при возможности.
2. Проверить на проде: /data/site.sqlite, /docs/, /scripts/, /uploads/test.php (создать и удалить) — должны быть 403/404.
3. Настроить ежедневный бэкап data/ вне webroot, шифрование и проверку восстановления.
4. Включить мониторинг ошибок и оповещения о новых заявках/обращениях по ПД.
5. Раз в квартал обновлять PHP и проверять зависимости; вести журнал доступов.
6. При росте обрабатываемых данных — рассмотреть 2FA, WAF, раздельные БД и роли.
